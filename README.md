# IQ & EQ Assessment Portal

This project contains a React student/reviewer interface and an Express/Mongoose API. Each IQ or EQ assessment contains 50 multiple-choice questions. Exam submissions remain pending until an authorized reviewer approves or rejects them. Scores and certification badges are only returned to students after approval.

## Local setup

1. Copy `.env.example` to `.env` in the project root.
2. Set `MONGO_URI` to your MongoDB Atlas connection string and `JWT_SECRET` to a unique random value of at least 32 characters. Keep `.env` private and out of version control.
3. To create the first reviewer account on a fresh database, set both `ADMIN_EMAIL` and `ADMIN_PASSWORD` (at least 12 characters). The server does not create an account with a built-in password. Existing admin accounts are not changed.
4. Install backend dependencies from `backend` with `npm install` and start the API with `npm run dev`.
5. Install frontend dependencies from `frontend/frontend` with `npm install` and start the UI with `npm start`; open `http://localhost:3000`.
6. Students can create accounts from the sign-in page. Reviewer accounts must be provisioned by an administrator.
7. Keep the backend running as a single process while students take exams. Active WebRTC signaling sessions are held in memory.

The backend defaults to port `9999`; set `REACT_APP_API_URL=http://localhost:9999` in the frontend environment for local development. Deployed frontend builds default to the configured Render API origin unless `REACT_APP_API_URL` is set in Vercel.

## Exam API

- `GET /api/exams/questions?examType=IQ|EQ` — returns 50 questions and their answer choices, never the answer key.
- `POST /api/exams/live-sessions` — authenticated student starts a camera-required session with a randomized 50-question set.
- `POST /api/exams/live-sessions/:sessionId/answer` — records the current answer (if any), enforces its one-minute server-side deadline, and advances to the next question.
- `GET /api/exams/live-sessions` — authorized reviewer list of active student sessions.
- `POST /api/exams/submit` — requires all 50 questions to have been reached and an active live camera session; the server uses its recorded answers and sets `Pending_Review`.
- `GET /api/exams/mine` — authenticated student's own history and approved certificate details.
- `GET /api/exams/pending` — admin/reviewer queue, including questions, submitted answers, and proctoring metadata.
- `PUT /api/exams/review/:id` — admin/reviewer decision. Approval requires a score from 0 to 100; rejection cannot include a score.

Mutating endpoints use the existing CSRF-token flow. Student requests cannot set their status, score, badges, or user ID.

## Live proctoring and exam rules

- Students must grant camera permission and have a live video track before they can begin. Video is sent peer-to-peer to a reviewer who joins the live session. It is not recorded or stored by the app.
- Each IQ and EQ bank contains 2,000 generated question variants. Students receive a random set of 50 and do not see the same question again until they have used the bank. Each question has a one-minute limit enforced by the backend; expired or skipped questions are recorded unanswered and cannot be revisited.
- A reviewer must be online to watch the test live. The signaling service uses a public STUN server; networks with restrictive NAT/firewall rules may additionally need a TURN service.
- Switching tabs, losing browser-window focus, camera-track termination, and a small set of recognizable screenshot keyboard shortcuts automatically submit a failed exam with the answers already entered.
- Browser APIs cannot reliably detect every screenshot or stop users switching tabs, using developer tools, changing browser settings, or capturing the screen with a separate device. These checks are best-effort deterrents, not a tamper-proof proctoring system.
- Live sessions use in-memory state and therefore require a single backend process. Horizontal scaling or multiple workers requires shared session storage and a Socket.IO adapter before deployment.
- The question sets use original critical-thinking and emotional-intelligence scenarios with generated variations. They are not standardized or validated IQ/EQ instruments; results require human review and must not be presented as professionally validated psychometric scores.

## Deploying to Render and Vercel

The Render Blueprint at `render.yaml` configures the API service, health check, and CORS origins for `https://testing-your-iq-and-eq.vercel.app`. The backend also allows this frontend origin by default. Connect the assessment repository to Render and deploy the Blueprint, then provide these secret/environment values in Render:

- `MONGO_URI` — MongoDB Atlas connection string.
- `ADMIN_EMAIL` and `ADMIN_PASSWORD` — initial admin account details; use a unique password of at least 12 characters.
- `JWT_SECRET` is generated by the Blueprint. Do not copy secrets into Git.

In Vercel, import the same repository and set the project root to `frontend/frontend`. The Create React App build and output directory (`build`) are detected automatically; `frontend/frontend/vercel.json` provides the SPA route fallback. Set `REACT_APP_API_URL` to `https://testing-your-iq-and-eq.onrender.com` in the Vercel project settings and redeploy.

For production cookie reliability, use custom domains on the same parent domain for the frontend and API (for example `portal.example.com` and `api.example.com`). The default `vercel.app` and `onrender.com` hostnames are cross-site, and browsers may block cross-site authentication cookies.

Render's health check is `/api/health`. Keep the backend's `trust proxy` setting enabled behind Render's proxy. Configure MongoDB Atlas network access for the Render service using the provider's current outbound IP guidance; do not expose the database to the whole internet as a shortcut.

This deployment configuration starts one backend instance. It is not a multi-instance or millions-of-users configuration: active live-exam state is currently held in process memory, Socket.IO is not using a shared adapter, and live video consumes reviewer and student bandwidth. Before adding backend instances, move live-session state to shared storage, add a shared Socket.IO adapter (for example Redis), and load-test the API, database, signaling, and live-video experience. The existing API rate limiter remains enabled; scaling should not depend on removing abuse protections.

## Security hardening checklist

This application now includes several runtime protections and a deployment checklist for the remaining infrastructure controls that must be set in the cloud.

1. Secrets Manager — implemented via environment variables and deployment secrets; no API keys or passwords are stored in code. Use managed secrets in Render, Railway, Vercel, or Azure/GCP/AWS secret stores.
2. Encryption in Transit — enforced with HTTPS/TLS expectations in production. Enable TLS certificates on the load balancer or reverse proxy and use modern TLS 1.2+ only.
3. VPC — required cloud-side architecture. Place the database and private app services in private subnets with no public ingress.
4. Security Groups / Firewalls — required cloud-side architecture. Allow traffic only from the load balancer and approved management endpoints.
5. Database Least Privilege — required cloud-side configuration. Create a DB user with only read/write permissions for the app's collections, and avoid broad admin roles.
6. Encryption at Rest — required cloud-side configuration. Enable encrypted volumes, encrypted MongoDB storage, and backup encryption.
7. Load Balancer (Reverse Proxy) — required cloud-side configuration. Use a single public entry point, terminate TLS, and keep origin servers private.
8. Input Validation & Sanitization — implemented in the backend with schema validation, email/name checks, request-body validation, and Mongo sanitization + XSS filtering.
9. Secure Authentication (AuthN) — implemented with signed JWT cookies and short-lived sessions; add MFA through a trusted identity provider for production.
10. Role-Based Access Control (RBAC) — implemented through route authorization for `student`, `analyst`, `reviewer`, and `admin` roles.
11. CORS Hardening — implemented with an allowlist of approved frontend origins and credentials restrictions.
12. Security Headers — implemented with Helmet, including HSTS, no-sniff, frame protection, and content security policy defaults.
13. Rate Limiting — implemented with Express rate limiting on `/api` traffic.
14. Web Application Firewall (WAF) — required cloud-side deployment. Put the frontend/backend behind a managed WAF to block SQLi/XSS patterns and malicious HTTP requests.
15. DDoS Protection — required cloud-side deployment. Use a CDN or edge network such as Cloudflare or a managed provider to absorb traffic spikes.
16. SSH/Access Bastion Host — required cloud-side access policy. Restrict SSH to private networks and a bastion/jump host only.
17. Dependency Scanning (SCA) — recommended for CI/CD. Add `npm audit` and a package scanning step in your build pipeline.
18. Container/Server Hardening — required deployment hygiene. Remove unused packages, restrict root access, and run only required processes in production.
19. Centralized Logging (SIEM) — recommended. Send app, access, and error logs to a centralized log platform for alerting and retention.
20. Anomalous Activity Alerts — recommended. Trigger alerts for repeated failed logins, unusual export volume, or unusual admin actions.
